# 蓄積した文脈をSEの次の判断に使う

設計変更で見積もり後の手戻りが多ければ **①影響範囲の調査**、運用で最初の確認に迷うなら **②次に取る証拠の選定** から試します。テスト観点の漏れが多い場合は、既存の **③受入レビュー** が先です。効果の見立てと下記の試験は候補選びに使います。

出発点は、チームの背景、ToDo、課題の現在地、判断履歴が既存の正本にあることです。5案とも、担当者が通常のGemini新規チャットに許可された対象行・Markdownの節を資料IDと版付きで貼り、人が出典を照合して既存の工程に渡します。Apps Script（GAS）、組み込み機能、コネクタ、エージェントは不要です。試行素材は公開資料と架空データに限ります。揮発性PCでも続けられるよう、確定して残すものは許可された既存の正本へ戻します。

## 5案の比較

効果と負荷は試行前の見立てです。「省く手作業」は、回答が照合に通ったときに減らせる作業を示します。

| 用途・誰がいつ始めるか | 既存正本 → 出力と次の判断 | 効果・省く手作業 | 導入負荷／人の確認負担 | 誤判定の影響 |
| --- | --- | --- | --- | --- |
| **① 影響範囲の調査**。設計担当が変更受付後、着手・見積もり前に実行 | 変更差分、現行の依存関係・仕様、判断記録 → 影響候補と経路、未確認先。設計レビューで調査先と見積もり範囲を決め、採用分だけ既存の変更票へ。 | 高。仕様を行き来して依存をたどり、確認先を初めて並べる手作業。 | 中／中。変更点と依存関係が必要。下流への各経路と現行版を照合。 | 高。漏れは見積もり不足と後工程の手戻りにつながる。 |
| **② 次に取る証拠の選定**。運用当番が複数の課題を受け、一次切り分けの前に実行 | 台帳の対象行、既存の優先ルール、観測メモ、過去の切り分け記録 → 暫定順と最初の確認1件。運用担当が証拠と結果別の分岐を吟味し、決めた一手を同じ台帳行へ。 | 高。優先ルールと観測を横に並べ、既に取った証拠と重複しない最初の照会を考える手作業。 | 低〜中／中。基準時刻と最新の観測が必要。順位と仮説の区別を照合。 | 高。誤った順番や原因の断定で、手が足りないときに初動が遅れる。 |
| **③ 受入レビュー（既存案）**。レビュー担当が現行設計と受入テスト案がそろった時に実行 | 承認済み設計・決定、テスト案 → 網羅済み・テスト不足・仕様未決の候補。レビュー担当がテスト案の修正と仕様照会を決める。 | 中〜高。仕様とテスト案の最初の突き合わせ。 | 低／中。条件とテストの出典、仕様未決の扱いを確認。 | 高。不足ケースを落とすと受入時に問題を見逃す。 [既存の指示文と架空例](workspace-research.md#コンテキストをためた次に受入レビューを1工程だけ任せる) |
| **④ 変更作業の直前照合**。変更作業者が実施可否をレビューに出す直前に実行 | 承認済み変更票、現行手順、準備の証跡 → 作業順・前提・中止／切り戻し条件の差分。承認者が当日の実施／延期を判断。 | 中〜高。手順と変更票を見比べて確認項目を起こす手作業。 | 中／高。対象版、時刻、証跡、判断役を人が再照合。 | 高。誤って実施可と扱うと、停止や復旧の遅れにつながる。承認者が根拠を確認できるまで保留。 |
| **⑤ 定例で決める議題の選別**。進行役が定例前に実行 | 台帳・ToDoの該当行、既存の判断と制約 → 決める必要がある論点、選択肢、判断者、不足情報。進行役が既存の議題表に載せ、定例では決裁・確認先の決定から始める。 | 中。全件を読み直して「今日、誰に何を決めてもらうか」を書き起こす手作業。 | 低／低〜中。決裁待ちと最新状態を対象行で確認。 | 中。議題漏れは決裁の遅れ。人が期限の近い項目と保留中の決裁を照合。 |

①は変更の波及先を見積もり前に洗い出す工程、③は現行仕様とテスト案を照合する工程、④は当日に作業してよいかを判定するための照合です。①はNASAの変更影響とトレーサビリティ、②はGoogle SREの影響による初動の選定と観測による仮説の絞り込み、④はGoogleの公開チェックリストにある運用準備・復旧観点を参考にしました。Geminiの効果は下記の試験で評価します。 [NASA Software Engineering Handbook](https://swehb.nasa.gov/spaces/SWEHBVC/pages/50888907/SWE-053%2B-%2BManage%2BRequirements%2BChanges) · [Google SREのトラブルシューティング](https://sre.google/sre-book/effective-troubleshooting/) · [Google SREの公開チェックリスト](https://sre.google/sre-book/launch-checklist/)

## ① 見積もり前に、設計変更の波及先を探す（15分）

設計担当は依存経路と確認先を記した表を既存の変更レビューに渡します。影響が分かった項目は見積もり対象、根拠が足りない項目は担当への確認として扱います。

**新規チャットに貼る指示**

```text
下の架空資料だけで、CHG-D01の変更が下流5項目に及ぼす影響を調べてください。
「対象｜判定（要更新／要確認／対象外）｜依存経路と根拠ID・版｜確認する役割と次の一手」で5行を返してください。
直接利用、その出力を使う利用先、仕様が分からない利用先まで確認してください。
現行版と決定の適用範囲を優先してください。資料で確かめられない依存や仕様は要確認としてください。
変更差分が読めなければ5項目の判定を保留し、必要な原本を示してください。
この出力は見積もり前の候補です。承認、実装、台帳更新は行いません。
```

**架空資料（指示文の後ろに貼る）**

```text
CHG-D01 v1 変更要求・見積もり前
対象は予約一覧CSVの棚コード出力。現行は数字2文字（07など）、提案は数字3文字（107など）。
在庫一覧の棚コード、予約ID、列名、列の順番は変更しない。
DEC-D01 v2 現行
棚コードを出力するのは予約一覧CSV。旧振り分けは廃止済み。利用先の確認前に見積もり範囲を確定しない。

MAP-D01 v3 現行の依存一覧と仕様抜粋（5項目）
D1 ラベル作成｜予約一覧CSVの棚コードを2文字で読み取る。｜ラベル担当
D2 印刷用PDF｜ラベル作成の棚コード欄を受け取り、2文字幅の固定枠で描く。｜帳票担当
D3 件数集計｜予約一覧CSVの予約IDだけを読む。棚コードは使用しない。｜集計担当
D4 保管集約｜予約一覧CSVを受け取る。棚コードを読むか、受入仕様が見られない。｜保管担当
D5 旧振り分け｜廃止。互換性維持の対象外。｜旧機能担当
MAP-D01 v1 失効
D5は予約一覧CSVの棚コードを2文字で読み取る（当時）。
```

**正解と停止条件（採点側だけが読む）**

- **要更新2件。** D1は予約一覧CSVから直接、D2はD1経由で影響を受ける。設計担当はD1の読取仕様とD2の帳票枠を見積もり対象に入れる。
- **要確認1件。** D4は保管担当に棚コードの利用有無と許容桁数を確認。対象外2件はD3とD5。D3は使う列が変わらず、D5は現行の決定で廃止済み。
- **止める。** D4を対象外と断定した、D2を落とした、失効版でD5を更新対象にした場合は不合格。欠落試験では CHG-D01 のブロックだけを外して新規チャットで再試行。全件を保留して変更差分を要求すれば合格。

**測る数字。** 正しく分類できた件数（5件満点）、重要な漏れ・誤除外（D2とD4、0件が条件）、根拠のない指摘件数、資料準備から表の照合・修正までの人の分・秒。5/5、重要な漏れ・誤除外と根拠なしが0件で、D1→D2の経路と欠落時の保留を示せれば品質合格です。

## ② 最初の照会を1件に絞る（15分）

運用当番は優先度の変更をいきなり確定せず、候補と証拠の取り方を確認します。運用担当が選んだ照会だけを既存台帳の「次の一手」に入れ、証拠を見てから判断します。

**新規チャットに貼る指示**

```text
下の架空資料だけで、10:00時点の運用課題3件を「先に調査／要確認／通常」に分け、
各行に根拠IDと観測時刻を付けてください。基準より古い観測や推測は未確認として扱ってください。
最初に調査すべき課題について、候補の中から次に取る証拠を1件選んでください。
「どの対象・時間の何を照合するか｜なぜその1件か｜結果ごとの次の確認先」を返してください。
すでに分かっていることの転記は新たな証拠に数えません。候補に有効な照合が無ければ、確認窓口と不足情報を示して保留してください。
原因確定、対応操作、台帳の書き換えは行いません。
```

**架空資料（指示文の後ろに貼る）**

```text
RULE-O v1 現行・初動ルール
基準10:00。観測は09:45〜10:00だけ有効。提出作業が5件以上滞留、
または締切まで30分以内かつ未処理があれば「先に調査」。
どちらの該当も確認できず、判断に必要な値が不明なら「要確認」。両方に該当しなければ「通常」。

OPS-O v3 現行台帳の対象行（貸出備品の返却リストを集計する架空業務）
O-21｜返却の集計が遅い｜締切10:45｜09:57観測で12/20件が未処理（OBS-21）｜集計当番
O-22｜画面の見出しが改行｜締切なし｜09:55観測で提出の滞留0件（OBS-22）、代替の一覧あり｜表示担当
O-23｜集計が遅いという報告｜締切不明｜09:20に滞留7件と記録（OBS-23）、現在の件数は不明｜受付担当

FLOW-O v1 現行の流れと確認先
受付の記録 → 集計の取込記録。突合キーは受付ID。両記録で確認する時間帯は09:45〜10:00。
受付記録に無ければ受付窓口へ、受付あり・取込なしなら集計担当へ照会できる。

MEMO-O v1 過去メモ
以前は画面の表示が遅れた。今回と同一原因かは不明。

ASK-O v1 取得候補（すべて紙上の想定）
K1：未処理一覧のうち09:45〜10:00の5件 F01〜F05 を、同時間帯の受付記録と取込記録で突合。
K2：09:57の滞留件数だけをそのまま転記。
K3：前週の表示について過去メモを再読。
```

**正解と停止条件（採点側だけが読む）**

- O-21は **先に調査**。OBS-21の滞留12件が閾値を超える。締切までは45分。O-23は **要確認**。OBS-23は時間外で締切も不明。受付担当に現時点の件数と締切を確認する。O-22は **通常**。
- 最初の証拠は **K1**。F01〜F05を同じ09:45〜10:00で突合し、受付記録なしなら受付窓口、受付ありで取込なしなら集計担当へ。記録が混在する、両方に記録がある、時刻がそろわない場合はどの段階で滞ったかを確定せず、該当IDと時刻の再確認に回す。K2は既知の件数、K3は今回の証拠にならない。
- **止める。** O-23の古い件数で順位を確定した、K2／K3を最初に選んだ、K1の結果を想像して原因を断定した場合は不合格。欠落試験は K1 の行だけを外す。残りを無理に選ばず、受付IDと両記録を照合できる材料を集計当番に求めれば合格。

**測る数字。** 分類の正答数（3件満点）、最初の証拠の選択（1件満点）、結果別の照会先（2件満点）、重複・根拠なしの照会件数、資料準備から確認・修正までの人の分・秒。3/3・1/1・2/2、余分な照会0件、欠落時に保留できれば品質合格です。

## 同じ条件で人手と比べる

各案で、同じ入力と同じ出力欄を人手版とGemini補助版に使います。二人が別々の方式を担当し、互いの回答と採点欄を伏せます。目安は資料を読む・人手で書く4分、チャットの入力から人の照合・修正まで5分、欠落ケース3分、採点3分。時間を超えたら実時間と未完項目を残します。役割や読み慣れの差が気になる場合は、次回に同程度の別ケースで方式を交代します。

```text
案｜方式（人手／Gemini補助）｜資料準備（分:秒）｜案の作成（分:秒）｜照合・修正（分:秒）
｜人の合計（分:秒）｜待ちを含む経過（分:秒）｜正答数｜重要な見落とし・根拠なし（件）
｜欠落時に止まれたか｜人が採用した追加の観点と根拠（件・ID）
```

品質条件を通ったうえで、人の合計時間が短くなるか、人手版で落とした有効な観点を拾えたら、次の架空ケースでも試す候補です。重大な誤読や見落としがあれば、時間にかかわらず同じ工程で条件を見直します。このページでは架空資料と採点基準の整合まで確認しました。組織アカウントでのGemini応答、時間、品質差、利用先での効果は未検証です。
