# Google Workspaceで、まず二人で一件

二人目が、口頭説明や前のチャットなしで、案件の現在地・決定理由・次の一手を説明できるかを試します。架空ケースは「案内カードの試し刷り」です。初回は15〜30分、翌回は10〜15分が目安です。

- Aは初回の記録担当兼決定者、Bは引き継ぐ担当。Aが採点し、翌回はBが台帳を更新します。
- [架空ケースと渡す資料](workspace-pilot/case.md) · [コピー用テンプレートと指示文](workspace-pilot/templates.md) · [採点と再試行](workspace-pilot/verification.md) · [Excel／Sheetsの完成見本と比較手順](workspace-pilot/spreadsheet.md)
- 想定は有料Google Workspace Enterprise、PCは揮発性。継続に要る原本とリンクは許可された共有先に置き、次回もブラウザから開きます。Sitesの設置と他者の閲覧は依頼者確認済みです。Driveの個別権限・Geminiの機能と設定・共有設定・Excelの動作は利用先で確かめます。
- 使う素材は公開資料と架空データ。Teams、外部連携サービス、AIエージェント、Apps Scriptを使わない手順です。公開GitHubはログインせずに閲覧し、取得が許される場合だけ取り込みます。試行資料の保存先は許可されたWorkspace内です。

## 1. どこに何を残すか

| 置き場 | 次の人が読む内容 | 誰がいつ確定するか |
| --- | --- | --- |
| チーム概要（Docs） | 目的、優先順位、制約、完了条件、判断できる役割 | 概要の責任者が初回に作り、目的・制約・権限が変わった時に更新 |
| 台帳（Sheets）の対象IDの1行 | 担当、状態、期限、誰の何を待つか、次の一手、判断記録へのリンク | 採番担当が起票時に1行を作成。現担当が進捗や保留の変化ごとにD/G/H列を更新。引き継ぎ受領時に旧担当がC/G/H列を更新 |
| 判断記録（Docsの案件別の節） | 採用・保留した案とその理由、根拠、見直し条件、有効な決定ID | 会議終了前に記録担当が提案と決定を仕分け、決定者が照合して確定。次回の決定時は新しい項目を追記し、旧項目に後継IDを記す |
| 資料一覧（Sitesまたは1枚のDocs） | 承認済み資料の原本リンク、版、適用範囲、管理者、閲覧対象。台帳と判断記録へ戻る入口 | 資料の管理者が承認・差し替え・失効時に更新。旧版は「失効／後継」を明記し現行一覧から外す |

現在の担当・状態・期限・行動は台帳の1行に置きます。判断記録には**判断と理由**を残し、台帳の状態を写しません。担当が進捗だけを変えた場合は台帳だけを更新します。判断が変わる場合は、決定者が判断記録を先に更新し、担当が同じIDの台帳を続けて更新します。途中で中断したり二つの原本が食い違ったりしたら、担当が決定者に照会し、更新を照合するまで確定回答を保留します。議事メモは資料の手掛かりです。個人のチャット出力は確認前の下書きとして扱います。

## 2. 初回の15〜30分

| 時間 | 担当と操作 | 詰まったとき |
| --- | --- | --- |
| 0〜5分 | Aが[既存のIssue台帳試作](../experiments/01-issue-tracker/README.md)に沿って試行用のSheetsを作り、Docsにチーム概要・判断記録・資料一覧を用意する。B自身が各原本を開けるか確認する。Sitesがあればリンクだけ載せる。 | Sites未設定なら資料一覧のDocsを起点にする。埋め込みが開けなければ直接リンク。Bが原本を開けなければ管理者・所有者に確認し、資料の権限を広げずに参照不能試験へ進む。 |
| 5〜12分 | Aが台帳に固定IDを採番し「未対応」→自分を担当にして「対応中」。ケースの古い提案N-01を会議メモとして読み、決定D-01を承認して判断記録に置く。案件を「確認中」にして待ち先・必要な証跡・次の一手を1行に残す。Bが受領したらC/G/H列を更新する。 | 文字起こしがなければ短い手書きメモで進める。台帳に編集できなければ下書きまで試し、権限者が同じIDの行を更新する。 |
| 12〜22分 | Bが資料一覧から初回セットを開き、Geminiを**新規チャット**で開始。最小構成は資料を一件ずつ手動で選ぶか、指定可能な架空の抜粋を資料ID付きで貼る。Bは回答の出典を自分で開いて確認し、自分の言葉で引き継ぎ内容を書く。Aは答えや口頭経緯を渡さず採点する。 | ファイル選択や添付が使えなければ、試行で使ってよい架空の抜粋を貼る。権限のない資料は貼らず「参照不能」と伝える。Gemini自体が使えなければ資料を人が読み、モデル項目を「未実施」とする。 |
| 22〜30分 | 新規チャットで参照不能のケースを試す。Aが[判定表](workspace-pilot/verification.md)に記録。Bが承認済みの根拠まで到達したかと、次に人が何をするかを確認する。 | 指定した資料が揃わない場合は手動経路を再試行する。根拠不明の回答から台帳や判断を更新せず、失敗箇所を記録する。 |

資料の指定は Driveの「Geminiに質問」→「ソース」→「追加」で個別に行えます。固定資料を試すときは「Geminiにソースの検索を許可」をオフにし、表示中の対象だけを確認します。画面に検索設定が見当たらない場合は、許可された架空の本文をIDと見出し付きで渡し、指定外の資料を使った回答は採点で弾きます。Geminiの参照は利用者のDrive権限と組織側の設定に依存します。Sitesにリンクや埋め込みを置いても、元ファイルは個別の権限で開きます。 [Driveでの資料指定と出典](https://support.google.com/drive/answer/16963068?co=GENIE.Platform%3DDesktop&hl=en) · [Geminiの参照条件](https://support.google.com/a/users/answer/17010577) · [Sitesの埋め込みと権限](https://support.google.com/sites/answer/90569?hl=ja)

## 3. 翌回の10〜15分

1. Bがケースの追加証跡E-01を受領し、同じIDの行のG/H列を更新します。「確認中」は続きますが、待ち先は資料担当から決定者に変わります。D-01は引き続き有効なので判断記録の追記は不要です。
2. Bが新規チャットに更新後の台帳行とE-01、ほかの固定資料を渡します。旧提案を残したまま「検証済み・承認待ち」を再現できるか採点します。古い回答の引用や以前のチャットは不要です。
3. Aが証跡と適用範囲を確認しD-02を承認、D-01には後継IDを記します。Bが同じ行を「対応中」にし、実施の記録E-02を照合した後に「完了」にします。G列は空欄、H列は更新日、J列は完了根拠D-02とE-02への参照。対象IDを検索して1行だけあることを確かめます。
4. Bがさらに新規チャットを開き、完了と承認の範囲、根拠を説明できるか確認します。二人で食い違った箇所だけ原本・権限・資料指定のどこで起きたか確認し、該当段階を再試行します。

「保留」には既存試作の状態「確認中」を使います。Formsを足すなら受付原文だけを回答一覧に置き、採番担当が同じ受付をI列で照合して1回だけ台帳に起票します。以後の状態や次の一手の更新先は台帳です。回答一覧と台帳の閲覧対象が違う場合、分けたブックで扱います。 [既存の列と状態](../experiments/01-issue-tracker/README.md) · [Formsの回答保存と個別権限](https://support.google.com/docs/answer/2917686?hl=ja)

## 4. 共通資料を参照する方法を選ぶ

最初は同じ資料ID・版・対象行を手動で指定し、二人が同じ答えと出典にたどり着けることを確かめます。承認済みの一覧は「原本へのリンク＋版・適用範囲」で作り、本文や現在地の複製は試行時の抜粋に限ります。資料の題名が似ていても日付だけで優先せず、承認状態・対象・後継IDを確認します。回答が古い資料や矛盾を指摘したら、確認した人が資料管理者に資料IDと該当箇所を渡し、管理者が原本と一覧を更新します。

| 方法 | 公開仕様と確かめ方 |
| --- | --- |
| Drive内のProjects | 共有するのはソース一覧。各人は空のチャットから開始し、元Driveファイルの閲覧権限は別途必要。Gmailの添付メール本文は共有相手のプロンプトに使われないため、共通資料は承認済みDriveファイルを個別にピン留めする。WebのDriveで「新規」→「新しいプロジェクト」、Bに閲覧権限を付与し、Bが原本と更新版を引用できるか試す。Drive内の利用には対象プランが必要。 [Drive Projectsの仕様](https://support.google.com/drive/answer/16684520?hl=en) |
| Workspaceの他アプリからDrive Projectsを指定 | Docs、Sheets、Slides、Chat、Meet、Gmail等のGeminiパネルからプロジェクトを呼ぶ方法。公式ヘルプ上は仕事・学校アカウント向けGemini Betaへのアクセスが必要。管理者の有効化と利用者の表示を確認し、Drive内の結果と別に採点する。 [アプリ横断利用の条件](https://support.google.com/drive/answer/16684520?hl=en) |
| Geminiアプリの共有Skills | Googleは2026年11月16日の告知で閲覧・編集の共有、Drive／Gemini Notebook／Google Photosの添付、DriveとNotebookの更新反映を案内。Driveの原本権限は別で、受信者は中身を確認して追加できる。告知ではWorkspace全顧客が対象で11月12日から段階展開、管理者は共有を無効化可能。個人と仕事・学校の**Gemsからの移行時期**も別で、Enterpriseは公式ヘルプで2027年3月。二人に画面と権限が揃う場合だけ、新規チャットで明示して比較する。普段の指示文はDocsに残す。 [公開告知](https://workspaceupdates.googleblog.com/2026/11/share-skills-add-files-from-Drive-Notebook-Photos-to-skills-Gemini-app.html?hl=pt_BR) · [共有操作](https://support.google.com/gemini/answer/17094296?co=GENIE.Platform%3DDesktop&hl=en) · [Gems移行](https://support.google.com/gemini/answer/18560919?hl=en) |
| 追加の製品・実装 | Gemini Notebookは資料を渡して調べる用途の比較候補。Google Cloudの **Gemini Enterprise** はMantel事例の横断検索・エージェントで使われる別製品。契約、管理者設定、資料権限を個別確認する。Apps Scriptによる同期・通知、Workspace Studioの自動化、組織横断検索はこの試行から外す。 [Mantel](https://cloud.google.com/customers/mantel) · [Workspace Studio](https://support.google.com/a/users/answer/16275487?hl=en) |

## 5. 人が開始し、人が確定する工程

Bが資料を指定して、試し刷り前の照会への一次下書きを依頼します。架空の作業範囲、配布の可否、費用の3問を使い、各問の下書き・出典・追加確認先を返させます。Aは各出典を開いて承認済みの記述と照合し、根拠がない行を「未回答」として返します。直したものだけをAが承認し、保存が必要な結論は案件の判断記録か対象行へ戻します。未確認事項を残したまま配布したり、自動で通知・更新・決裁したりする操作はありません。 [照会と指示文](workspace-pilot/templates.md) · [合格条件](workspace-pilot/verification.md)

表計算では、完成見本の書式・数式・印刷範囲を固定し、LLMの提案を担当者が入力セルに値として取り込みます。GoogleはGemini in Sheetsで数式や表の作成等を案内していますが、対象プランが必要で、ExcelファイルでGemini機能を使う場合はGoogle Sheetsに変換するよう案内しています。見本と同じ仕上がりになるかは、利用先のExcelで再計算と印刷プレビューを確認し、同じ条件で人の作成時間と比較します。 [Gemini in Sheets](https://support.google.com/docs/answer/14356410) · [完成見本と測定](workspace-pilot/spreadsheet.md)

## 6. 公開事例から取り入れた工程

| 事例で確認できたこと | この試行で試す運用 |
| --- | --- |
| BeyondはMeetの文字起こしを知識ベースに加え、情報提供依頼（RFI）の下書きにDriveの案件資料を使う。Geminiが古い・誤った資料を返すと、チームが更新対象にする。RFIツールはGemsとNotebookLMの試行に取り組んだ小グループの成果として紹介される。 [Google WorkspaceのBeyond事例](https://workspace.google.com/customers/beyond/) | 会議後に事実を確認して残す→資料を指定して下書き→古い記述が出たら管理者へ返す、を人の操作で試す。記事からは更新責任者・承認フロー・同じ案件を新規チャットで継続できるかは分からない。 |
| Equifaxは一部のチームがMeetの要約・作業項目を欠席者と共有。 [Equifaxの運用](https://workspace.google.com/blog/customer-stories/equifax-embraces-gemini-for-secure-innovation-across-business-units) | 会議終了時点でAが決定と提案を区別し、Bが翌回に使うのは確定済みの項目と現在の台帳行。Meetの自動メモはこの試行の前提から外す。 |
| MERGEは顧客データやアイデア入りの初稿から共同作業を開始。 [MERGEの運用](https://workspace.google.com/blog/customer-stories/google-workspace-gemini-allows-merge-build-innovative-effective-and-creative-team) | Bが同じ固定資料から一次草稿を作り、Aが不足を残して承認する。記事では正本の対象や改訂担当までは確認できない。 |
| Mantelでは主担当がNotebookLMで資料を執筆者に渡し、執筆者が質問して初稿を進める。案件履歴の横断検索と複数システムを使うSOWエージェント試行にはGoogle CloudのGemini Enterpriseを利用。 [Google CloudのMantel事例](https://cloud.google.com/customers/mantel) | 「次の人に資料を渡し、次の人が質問して続ける」工程を引き出し、権限と版を含めて固定資料で検証する。横断検索やエージェント工程は別の構成。 |

この手順は上の事例から組み立てた試行案です。現場への接続・導入や、組織アカウントでのGemini、共有機能、Excel実機の実行は行っていません。判定は[採点表](workspace-pilot/verification.md)を利用先で実施して記録してください。
