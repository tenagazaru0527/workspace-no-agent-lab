# P0：Issue台帳を Google Workspace だけで作る

**最小構成は Sheets。** Sites は入口と案内、Forms は受付、Sheets は台帳と集計です。Sites に Issue を保管するわけではありません。P0 には Apps Script、外部 API、アドオン、AI エージェントを使いません。

## 1. 台帳（すぐ試せる範囲）

1. 組織が認めた Google Workspace 内で新しい Sheets を作り、1枚目のタブを「台帳」にします。
2. [架空データ CSV](sample-issues.csv)を台帳にインポートするか、下の列名を A1 から作ります。日付列 F/H は日付形式にして、CSV の日付が文字列になっていないことを確かめます。
3. 1行目を固定します。D2:D に状態（未対応、対応中、確認中、完了、見送り）、E2:E に優先度（高、中、低）のプルダウンを作り、候補以外の入力を拒否にします。確認中は、確認内容と相手を「次の一手」に書いた場合だけ使います。
4. 採番は当面1人に集約します。IDは LAB-001 のような固定文字列とし、行番号で採番しない・一度使った番号は再利用しない・完了行を削除しない。担当別には「データ → フィルタ表示」を使用し、台帳全体の並びや表示を他の人に押し付けないようにします。
5. 終了時は「完了」または「見送り」とし、J列に理由・根拠を残します。詳細な履歴が必要なら「履歴」タブを追加し、記録日｜ID｜変更者｜変更前｜変更後｜理由・根拠を手動追記。これは監査用の改ざん不可ログではありません。

列（A〜J）：ID、件名、担当、状態、優先度、期限、次の一手、更新日、起票元・資料、完了・見送り理由。

### 集計タブ

「集計」を作り、A2:A6 に 基準日／未完了／期限超過／担当未設定／重複ID行数、B2:B6 に以下を入れます。初期 CSV に対して B2 を `=DATE(2026,12,3)` にしたときの期待値は **3、1、0、0**。期限超過に当日期限と期限なしは含みません。稼働時は B2 を `=TODAY()` に置き換えます。式の引数区切りはスプレッドシートの言語設定に合わせてください。

```text
=DATE(2026,12,3)
=COUNTIFS('台帳'!A2:A,"<>",'台帳'!D2:D,"<>完了",'台帳'!D2:D,"<>見送り")
=COUNTIFS('台帳'!A2:A,"<>",'台帳'!F2:F,">0",'台帳'!F2:F,"<"&B2,'台帳'!D2:D,"<>完了",'台帳'!D2:D,"<>見送り")
=COUNTIFS('台帳'!A2:A,"<>",'台帳'!C2:C,"",'台帳'!D2:D,"<>完了",'台帳'!D2:D,"<>見送り")
=IF(COUNTA('台帳'!A2:A)=0,0,COUNTA('台帳'!A2:A)-COUNTUNIQUE(FILTER('台帳'!A2:A,'台帳'!A2:A<>"")))
```

## 2. Forms を足す（受付が必要なら）

- 架空の起票フォームを作り、項目は「件名（必須）・背景と希望（必須）・希望期限（任意）」だけ。ファイルのアップロード、外部ユーザー、メールの自動収集は最初の試験に不要。
- Forms の「回答 → スプレッドシートにリンク」で同じブックに回答を保存。自動作成される回答タブを受信箱にし、**台帳タブとは分離**。担当者が内容を確認したものだけ固定IDを付けて台帳に起票します。台帳編集を起票者に付与する必要はありませんが、回答タブと台帳が同じブックなら**ブック閲覧者は回答タブも見られる前提**です。受付原文を広く見せないなら、受信箱を別ブックに分け、台帳へ必要部分だけ転記します。

## 3. Sites を足す（入口が必要なら）

- Sites に「新規起票」「台帳を開く」「運用ルール」の3項目を置きます。集計を見せる必要があれば、許可された一覧または集計を「挿入 → スプレッドシート」で追加します。埋め込みが制限されていれば、同じ権限で開く通常リンクを使います。
- Siteの閲覧者、Formの回答者、Sheetの閲覧者・編集者をそれぞれ必要な担当者・承認済みグループに設定します。**Sites に載せたことは Sheets への権限付与を意味しません。** リンクや埋め込みを見せるために「ウェブに公開」や「リンクを知っている全員」に切り替えないでください。タブを隠す、フィルタを掛ける、編集を保護するだけでは閲覧範囲を分けられません。
- 閲覧専用・起票用・編集用・権限なしのケースを [チェック表](verification.md) で確認します。

## 向いている範囲

少人数で、担当と状態を一覧して対応漏れを防ぐ用途。GitHub Issues と異なり、チケット単位の権限、スレッド、履歴の強制、PR連携、通知はこの手順ではつきません。チケットごとの閲覧制限や正式な監査証跡が必要な業務には、このまま採用しません。
